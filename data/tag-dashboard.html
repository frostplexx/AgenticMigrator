What the categories mean

applied — the migration is present in the migrated output. For the manifest-mechanical migrations this is a final-state observation (the converter applied them before the agent ran); for the rest it is agent-attributable work reconstructed from the transcript.

skipped — needed but not applied: the MV2 extension had the feature, the migration did not convert it. The pipeline's own ledger records why: platform impossible in MV3, limited partially expressible, abstained the agent declined the capability, unexplained needed but not applied with no reason on record — the failure mode.

spurious — the mirror image of skipped: applied but never needed. The migrated output contains the change although the original extension never had the feature that requires it. Example: an offscreen document scaffolded for a background script that never touched DOM APIs, or a host_permissions block added when the source had no URL permissions to split. Over-application of a template without its trigger; usually harmless at verification time (skips drag verdicts down, spurious do not).

repair — a separate event channel: fixes the LLM made during the run's repair phase, counted per extension, not attributed to a single migration.

Skip reasons per migration

How a skip gets its reason

Every skip here is a change the ledger scored needed && !applied — the MV2 extension had the feature and the migration did not convert it. The reason is assigned once, in priority order (skipReason in src/host/tags.ts):

platform MV3 removed the capability outright — e.g. reading response bodies or running remotely hosted code. The only faithful migration is to leave it out, so the framework skips it on purpose; this is a fact about Chrome, not a failure. Each such tag carries the Chrome docs URL as evidence, so the claim is checkable.

abstained the agent declined, in writing — it produced an ABSTAIN.md whose text names the capability (matched by per-change word patterns). The agent's own word outranks the support table: it is a claim with evidence attached, so it takes precedence over the two categories below. The ABSTAIN.md excerpt is kept on the tag.

limited MV3 supports it only partly — an equivalent exists that covers the common cases but not the rest, e.g. declarativeNetRequest expresses static block/redirect rules but cannot decide anything from the request at request time. Whether a given skip here is the platform's doing or the model's needs the evidence read before it is counted either way.

unexplained needed but not applied, no reason on record — MV3 has a full equivalent (e.g. eval() is always rewritable), so not applying it is a defect of the migration: the framework met this change and moved on. This is the failure mode a load-only verifier cannot see, and it dominates: 243 of 312 skips.

Priority order: platform → abstained → limited → unexplained. A skip of a full-support change is never the platform's; a partial-support skip without an abstention stays unattributed (limited) rather than being guessed.
